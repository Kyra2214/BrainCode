# 07 — n8n-io/n8n

## Pente fino adicional

O n8n mostra uma regra importante para o Braim: **integrações são dados/configuração executável, não lógica espalhada no core**. O Node/Connector deve declarar contrato, credencial e comportamento.

### Generic HTTP como último recurso

Um `GenericHttpTool` permite descobrir/testar APIs ainda não catalogadas. Depois de validada uma API recorrente, o Brain pode promover o recurso a adapter específico.

### Credential abstraction

Credencial não deve viajar dentro do prompt. Tool declara `credential_ref`; o executor resolve o segredo de forma segura. O LLM nunca precisa conhecer o valor secreto.

### Execution history

Cada node/execution precisa de entrada, saída, duração, erro e estado. Isso alimenta o sistema de aprendizado do Braim.

### Human gates

Aprovação humana deve ser uma transição de estado, não um `if` dentro de cada integração.

## Objetivo

Estudar automação, integrações, nodes, workflows, aprovação humana, observabilidade e flexibilidade de providers.

## O que mais interessa

n8n apresenta uma arquitetura de workflows composta por nodes. O projeto atual informa mais de 1500 integrações e milhares de templates. Há suporte a AI workflows, agentes, ferramentas, código JavaScript/Python e self-hosting.

## Principal aprendizado para o Braim

O Brain não deve implementar cada integração dentro do core. Deve possuir um catálogo de capabilities e adapters/tools.

```text
Brain
 ↓
Capability
 ↓
Tool/Connector
 ↓
Provider/API
```

## Nodes

Cada node possui uma capacidade bem definida. Esse padrão é excelente para o futuro `ToolRegistry` do Braim.

Um Tool deve declarar:

- input schema;
- output schema;
- credenciais exigidas;
- permissões;
- efeitos colaterais;
- retry;
- timeout;
- rate limit;
- provider;
- versão.

## HTTP Request

O node HTTP Request demonstra um fallback genérico importante: quando não existe integração dedicada, o sistema pode chamar uma API diretamente. Para o Braim isso vira `GenericHttpTool`.

Mas, assim como n8n recomenda nodes dedicados quando existem, o Braim deve preferir adapters específicos quando houver conhecimento suficiente.

## Workflows

Um workflow é uma composição de operações. Isso complementa o planner do Braim:

```text
Roadmap item
  ↓
Workflow
  ├── pesquisa
  ├── geração
  ├── execução
  ├── teste
  └── entrega
```

## Human-in-the-loop

n8n possui mecanismos de aprovação humana. O Braim deve ter um ponto de pausa quando uma operação tiver alto impacto: publicação, exclusão, acesso sensível, compra, envio de mensagem etc.

## Observabilidade

Cada node e execução precisa ter estado. O Braim deve registrar isso desde o primeiro fluxo.

## O que absorver

- Tool/Node registry;
- connectors;
- generic HTTP fallback;
- workflow graph;
- retries;
- execution history;
- human approval gates;
- credentials abstraídas;
- templates de workflow;
- versionamento;
- observabilidade;
- promoção de Generic Tool para Adapter validado.

## O que não absorver

- editor visual inteiro;
- 1500 integrações dentro do Brain;
- licença/serviços proprietários;
- arquitetura completa do n8n.

## Conclusão

n8n mostra como transformar APIs e serviços em blocos reutilizáveis. O Braim deve absorver essa ideia em uma versão menor: **capability → tool → workflow → execução**, com credentials seguras, histórico observável e aprovação como estado.
